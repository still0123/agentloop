# 上下文管理评估

本文记录上下文管理机制的固定离线回放结果。评估对象是归档、采样、增量摘要、用户请求
ledger 和失败重放的控制流程；不用于衡量真实模型的回答质量、费用或端到端任务完成率。

## 方法

回放脚本以相同输入和固定 Mock 风格响应，对比基线提交 `5154aa2` 与实现提交 `87316f6`。
指标为序列化消息的字符数，而不是 token 数。脚本和原始记录均保存在仓库中：

- [回放脚本](../scripts/benchmark_context_policy.py)
- [原始 JSON](evidence/context-policy-replay.json)
- [行为测试](../tests/test_context_policy.py)

运行：

```bash
.venv/bin/python scripts/benchmark_context_policy.py
```

该脚本会从 Git 读取基线实现；运行环境需要拥有对应历史提交。模型调用为固定离线响应，
不访问模型服务。

## 结果

| 场景 | `5154aa2` | `87316f6` |
|---|---|---|
| 最新工具输出为 120,000 字符 | 处理后消息 120,458 字符，仍超过 50,000 字符限制；调用摘要 1 次 | 处理后消息 1,577 字符；未调用摘要；原文归档且可逐字回读 |
| 摘要输入中的日志中部错误与尾部标记 | 两者均未出现 | 两者均出现 |
| “只读”请求后继续执行，固定摘要遗漏早期约束 | 压缩上下文不包含早期只读要求 | 有序 `user_requests` ledger 保留早期原文 |
| 第二次增量摘要失败 | 没有待处理历史重放状态 | 保留旧摘要，记录待处理归档；下一次摘要重放后清空 |

首项的消息字符数从 120,458 降至 1,577，约减少 98.69%。尾部错误在两版输出中可见；
新实现还保留完整工具原文以供后续读取。消息字符数只说明压缩后的请求体规模，不能直接
换算 token 用量、调用费用或延迟。

## 实现验证

提交 `87316f6` 上执行了完整回归套件：Python 3.11 环境下 `pytest -q` 输出为
**144 passed**，Ruff 检查通过。该结果验证的是实现行为，包括中文预算、工具调用与结果
配对、摘要采样、失败后的待处理归档重放、内部消息隔离和定向回读边界。

固定离线响应无法证明真实模型能稳定保留语义，也无法给出跨方案的成功率、成本或延迟
排名。要获得这些结论，需要在相同模型、相同任务集和相同输入预算下，额外记录提供商
实际用量、任务完成率、约束遗漏率、归档回读成功率、总调用成本和端到端耗时。
